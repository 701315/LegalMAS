## СХЕМА ВЫХОДА
{
  "overall_assessment": "2-4 предложения: общая картина, полнота покрытия, режим проверок, общее число рисков по уровням",

  "next_actions": [

## ПРАВИЛА СОСТАВЛЕНИЯ

### Обязательные правила:
1. Используй ТОЛЬКО факты из данных. Не выдумывай документы, суммы, даты, стороны, условия.
2. check_ids и linked_check_ids — ТОЛЬКО коды из блока material_checks данных.
3. Не меняй severity: используй severity соответствующей проверки из данных.
4. Каждый critical-риск из данных ОБЯЗАН попасть в risk_claims.
5. Группируй однородные риски (один check по нескольким документам или группа
   документов одного типа) в один claim с указанием affected_docs_count.
6. risk_claims: от 1 до 6 пунктов, отсортированы по убыванию severity, затем по убыванию affected_docs_count.
7. next_actions должны быть привязаны к конкретным check_ids через linked_check_ids.

### Запрещено:
- Делать юридических выводов и рекомендаций, которых нет в данных.
- Писать "рисков нет", если часть корпуса не обработана.
- Использовать воду и канцелярит: "анализ был проведён", "следует обратить внимание на некоторые аспекты".
- Дублировать один и тот же риск в нескольких claims.

### Обработка edge cases:
- Если critical рисков нет — risk_claims начинается с high.
- Если покрытие неполное (failed / quarantine / pending_review > 0) — limitations
  ОБЯЗАНЫ содержать явное описание ограничения с указанием количества проблемных документов.
- Если нет ограничений покрытия — limitations = [].

## КРИТЕРИИ КАЧЕСТВА
Хороший claims plan:
- Каждый claim можно проверить по исходным данным.
- Нет двух claims с одинаковым check_id.
- next_actions конкретны и исполнимы (не "провести анализ", а "запросить у контрагента пояснения по...").
- overall_assessment даёт читателю полную картину за 10 секунд чтения.

## ФОРМАТ ОТВЕТА
Верни ТОЛЬКО JSON, без пояснений и без markdown. Никаких комментариев до или после JSON.
