Нам нужно зафиксировать единый «язык триггеров», чтобы Stage 6 и Stage 8 говорили одними и теми же идентификаторами. Ниже — как оформить это как правило и как действовать при рефакторинге и для новых типов.

Цель рефакторинга
Добиться, чтобы любой триггер имел один канонический ID, который:

объявлен в trigger_definitions в YAML конкретного типа;

этот же ID используется:

в exclusion_logic.condition;

в conditional_checks.trigger;

и именно он попадает в applicable_triggers в БД (из Stage 6).

Тогда в Runner/ValidationEngine можно будет оперировать триггерами без костылей типа маппингов, и логика «сработал триггер → выполняем правило» будет прямой.

Правила для рефакторинга существующей инструкции
Выделить канонический список триггеров

В каждой инструкции (например, contract_1.6_real_estate.yaml):

Просмотреть блок trigger_definitions и зафиксировать все ID триггеров, например:

residential_property

land_plot_sale

building_sale

share_in_right_sale

legal_entity_party

individual_party

mortgage_related

lease_related

foreign_buyer_keywords

agricultural_land_keywords

border_zone_keywords

mcd_common_property_sale

Это и есть канонические идентификаторы для данного типа.

Проверить exclusion_logic

В блоке validation_engine_v3_2.exclusion_logic убедиться, что в condition используются ровно эти же ID.

Если там уже строки вида:

text
exclusion_logic:
  - condition: "agricultural_land_keywords AND foreign_buyer_keywords"
    target: "rejection"
    ...
  - condition: "border_zone_keywords AND foreign_buyer_keywords"
    target: "rejection"
    ...
— ничего менять не надо, это уже канонично.

Проверить conditional_checks в essential_elements

Найти все conditional_checks внутри essential_elements, например:

text
essential_elements:
  - element: "subject"
    ...
    conditional_checks:
      - trigger: "real_estate_keywords"
        keywords: [...]
        rule: "cadastral_number_required"
        ...
Здесь real_estate_keywords не существует в trigger_definitions. Нужно:

Вариант A (простой):

Выбрать наиболее подходящий существующий триггер (например, residential_property или real_estate_any, если он будет заведён).

Заменить:

text
conditional_checks:
  - trigger: "residential_property"
    keywords: [...]
    rule: "cadastral_number_required"
    ...
Вариант B (агрегирующий):

Если нужен триггер «любая недвижимость», добавить его в trigger_definitions:

text
trigger_definitions:
  real_estate_any:
    any_keywords:
      ["недвижимость", "квартира", "участок", "здание", "сооружение", "помещение"]
  ...
И использовать тот же ID в conditional_checks:

text
conditional_checks:
  - trigger: "real_estate_any"
    rule: "cadastral_number_required"
    ...
Проверить, что нет «одиночных» имён

Быстро просмотреть YAML на предмет любых идентификаторов, которые выглядят как триггер, но не объявлены в trigger_definitions:

в exclusion_logic.condition (строки с ... AND ... / OR и т.п.);

в conditional_checks.trigger.

Если такое имя встречается — либо:

завести для него запись в trigger_definitions,

либо заменить на уже существующий канонический ID.

Правила для новых типов договоров и документов
Когда будешь писать новые contract_X.Y.yaml / другие типы:

Всегда начинать с trigger_definitions

Сначала придумать и зафиксировать список триггеров в trigger_definitions:

text
trigger_definitions:
  residential_property:
    any_keywords: ["квартира", "жилой дом", ...]
  mortgage_related:
    any_keywords: ["ипотека", "залог", ...]
  ...
Эти имена — «истина» для данного типа.

Использовать те же ID в логике

В validation_engine_v3_2.exclusion_logic:

В condition использовать только ID из trigger_definitions, например:

text
exclusion_logic:
  - condition: "mortgage_related AND foreign_buyer_keywords"
    target: "rejection"
    ...
В essential_elements.*.conditional_checks:

В trigger тоже только ID из trigger_definitions:

text
essential_elements:
  - element: "subject"
    conditional_checks:
      - trigger: "residential_property"
        rule: "residents_list_required"
        ...
Не придумывать «локальные» имена триггеров

Не вводить trigger: "xxx" в conditional_checks или упоминать "xxx" в exclusion_logic.condition, если нет:

text
trigger_definitions:
  xxx:
    any_keywords: [...]
Если нужно новое условие:

сначала добавить новый триггер в trigger_definitions,

затем использовать его ID в conditional_checks и/или exclusion_logic.

Держать имена «функциональными»

Имена триггеров должны быть по смыслу признака, не по технической детали:

residential_property, land_plot_sale, agricultural_land_keywords, foreign_buyer_keywords — хорошо;

trigger1, real_estate_keywords_v2 — плохо, их сложно переиспользовать и интерпретировать.
